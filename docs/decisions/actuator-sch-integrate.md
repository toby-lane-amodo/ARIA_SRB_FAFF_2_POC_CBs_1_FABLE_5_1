## 2. Root sheet layout - DEC-0022

The root is the block diagram of `docs/FAFF-2-Electronics-Full.svg` read left to
right: 24 V in at the top left, sensing and user I/O down the left column, the
STM32H723VET6 in the middle, motor drive on the right.

**Every peer block's pin rows are aligned with the mcu rows they face.** That is
the whole trick: 48 of the 55 nets are point-to-point between the mcu and one
peer, so if the mcu's left-side pin order matches the stacking order of the left
column, and the mcu's right-side order matches motor_drive's, every one of those
wires is a single straight horizontal segment. No bends, no crossings, no
junctions, and the reader can follow any net across the page without tracing.

Two topologies needed more than that.

**`power_entry_24v` fans out to three different places.** Its three sheet pins sit
on a 5.08 mm pitch rather than the usual 2.54 so the routes can nest: `V24_LOGIC`
straight across to `power_rails`; `+24V_SW` peeling down at `x = 96.52` and
running along `y = 45.72`, above the mcu block and below `power_rails`, all the
way to `motor_drive`; `V24_MON` dropping inside that at `x = 86.36` into the
mcu's topmost left pin. Nested that way, no two of the three cross.

**The shared SPI2 CONFIG bus is tapped once per wire.** `CONFIG_SPI_SCK`, `_MOSI`
and `_MISO` leave the mcu's right side, run to `motor_drive`, and each is tapped
at a junction that drops to `temp_sense`. `ADS1120_nCS` follows the same corridor.
The four drops are at `x = 248.92, 246.38, 243.84, 241.30` - outermost drop for
the highest row on both ends - so the four routes nest and nothing crosses.

**That is why `temp_sense` sits under `motor_drive` rather than in the sensor
column.** It hangs off the same shared SPI2 bus as the DRV8323 (`ARCHITECTURE §5.1`),
so the bus is drawn once with two loads on it. Its two probe channels never leave
its own sheet, so nothing is lost by moving it off the sensor side.

The root sheet is generated by **`tools/gen_root_sheet.py`**, re-runnable and
deterministic: every uuid is a `uuid5` of a stable key, and the ten sheet-symbol
uuids are hard-coded because every child sheet's symbol instance paths reference
them (`/<root-uuid>/<sheet-uuid>`; get that wrong and the sheet loads with almost
nothing connected).

### 2.1 Interface reconciliation

Two contracts disagreed between blocks and had to be settled here.

**`CONFIG_SPI_MISO` shape.** `motor_drive` declared it `output`, `temp_sense`
`tri_state`, and `actuator-sch-afe.md §3` explicitly flagged the clash for
integration. Both are `tri_state` now, which is what the wire actually is: three
devices share it and each drives only while its own chip select is low. One token
changed in `motor_drive.kicad_sch`; no connectivity moved.

**`RAIL_PGOOD` had no consumer.** `power_rails` exported it as a hierarchical
label for "the `test_debug` rail probe header and a future MCU GPIO", but `J402`
carries `+5V`, `+3V3`, `+3V3A` and three grounds and has no seventh way, and
`OQ-07` has never allocated the GPIO. A sheet pin on a one-endpoint net is an ERC
error, so it is demoted to a **sheet-local label** - `D303` and `TP308` still
observe it, which is where `DEC-0007` puts the producer's own test point anyway.
**`OQ-07` stays open**; re-promoting the label is a one-line change once a pin
exists. No requirement asks for PGOOD at the MCU, so this blocks nothing.

### 2.2 What the root deliberately does *not* wire

`GND`, `+5V`, `+5VA`, `+3V3` and `+3V3A` are Amodo power symbols and connect
globally. `power_rails` produces all four rails and owns their `PWR_FLAG`s;
`power_entry_24v` owns the flags for `GND` and `+24V_SW`. Only `+24V_SW`,
`V24_LOGIC` and `V24_MON` leave `power_entry_24v` as ordinary nets.

## 3. Power-symbol designators - DEC-0024

`loadcell_afe` and `temp_sense` had both annotated from `#PWR001`, so 19 of their
power symbols shared a reference. KiCad raises nothing for this - `#`-prefixed
references never reach the netlist - but two sheets' symbols silently become one
component set, which is exactly the failure `AGENTS.md` already warns about for
ordinary designators. Renumbered to the sheet ranges every other block already
used: `#PWR5xx` for `loadcell_afe`, `#PWR7xx` for `temp_sense`. All 272 power and
flag references across the ten sheets are now unique, asserted programmatically.

The rule is now written into `AGENTS.md`: **power symbols follow the same
per-sheet hundreds range as ordinary designators.**

## 4. The DRV8323S land pattern - DEC-0025

Owed since the motor block landed. `SLVSDJ3D` (the DRV832x data sheet) ships the
`RTV0032E` and `RGZ0048A` package drawings and **not** `RTA0040`'s, which is why
`D-MOT-01` deferred the footprint. TI's own `MPQF134A` drawing for the RTA package
is the 2004 single-page style: it gives the outline but not the land pattern, and
refers the thermal-pad dimension back to the data sheet that omits it.

Found the modern drawing in a sibling data sheet: **TI 4219112/A (07/2018),
`RTA0040B`**, in the DRV8353 data sheet pp. 98-100. Committed as
`datasheets/DRV832x_RTA0040B_package_4219112A.pdf` so nobody repeats the hunt.

Set beside **TI 4219052/A (06/2016), `RHA0040B`** (msp430g2755.pdf p.72), the two
are the same land pattern:

| | RTA0040B | RHA0040B |
|---|---|---|
| Package height | WQFN 0.8 max | VQFN 1 max |
| Body | 6.1 / 5.9 square | 6.1 / 5.9 square |
| Pitch | 36X 0.5 | 36X 0.5 |
| Terminal span | 2X 4.5 | 2X 4.5 |
| Terminal | 40X 0.5/0.3 long, 0.28/0.16 wide | 40X 0.5/0.3 long, 0.27/0.17 wide |
| Exposed pad | 4.15 ±0.1 | 4.15 ±0.1 |
| Land | 40X (0.6) × (0.22) inside (5.8) | 40X (0.6) × (0.22) inside (5.8) |
| Stencil | 9X (1.17) on (1.37), 71 % | 9X (1.17) on (1.37), 72 % |

Only the package height differs, and that touches the 3D model, not the copper.
So KiCad 9's official `Texas_RHA0040B` footprint is a **dimension-verified base**,
which is what `pcb-layout-style` allows; its perimeter pads, silkscreen, fab
outline and courtyard are reproduced by `tools/gen_rta0040b_footprint.py`.

Two deliberate departures from that base:

* **Stencil apertures are TI's own** 9X (1.17) on (1.37) TYP with (R0.05)
  corners, not KiCad's 1.12 on 1.38 - 71.5 % coverage against TI's stated 71 %.
* **Perimeter pads stay IPC-nominal** (0.875 × 0.25 on a 2.9375 row offset)
  rather than TI's tighter (0.6) × (0.22) on 2.6. That matches the house QFN
  footprints in `Amodo.pretty`, and the 0.375 mm of toe outside the body edge is
  what makes the joint inspectable. It is a superset of TI's own land, so the
  vendor pattern is fully covered.

Asserted programmatically after generation: 40 pads, ten a side, 0.5 mm pitch,
4.5 mm span, 2.9375 row offset, EP 4.15 square, 9 apertures at 71.5 %. Pin 1 is
the top pad of the **left** column with numbering anticlockwise - `SLVSDJ3D`
figure 6-6, the DRV8323S **top** view - and the project-local `DRV8323S` symbol's
41 pins (pin 41 = `PAD`) match that figure name for name.

The 3D model points at KiCad's RHA body of the same outline: 0.2 mm proud of the
RTA's 0.8 mm maximum, which is conservative for clearance and is stated in the
footprint `descr`.

`FPLifecycle` is `draft`. The PCB wave should confirm the land against a real
part before the first order.

## 10. Open items for the captain

Nothing here blocks the PCB wave; all four want a ruling before the board is
ordered.

1. **`OQ-07` - `RAIL_PGOOD` has no MCU pin.** Today it drives an LED and a test
   point inside `power_rails` and nothing else. Spare MCU pins exist
   (`SPARE_PA8/PA10/PB4/PB7/PC13/PE3/PE7`). Allocating one is an `.ioc` revision
   plus one label in each of two sheets. §2.1.
2. **`AM26LV32CDR` is obsolete.** TI's package addendum in
   `datasheets/AM26LV32.pdf` (14-Oct-2025) lists `AM26LV32CD`, `AM26LV32CDRG4`
   and `AM26LV32ID` as Obsolete. The active SOIC part is **`AM26LV32IDR`** -
   same D package, wider temperature range (−40 to 85 °C). Changing the `mpn` is
   a part-selection call and needs a JLC stock check, so it is raised, not made.
   The footprint is unaffected.
3. **88 components carry no datasheet URL.** All are Amodo house-library
   passives and test points whose `Datasheet` field is blank or `~` **in the
   read-only house library**. `schematic-style` requires a working web URL on
   every library part, so this is an upstream library fix for the captain, not a
   project one - overriding 88 instances locally would diverge from the house
   library for no gain.
4. **DRV8323S land pattern is `FPLifecycle draft`.** Confirm §4's reasoning, and
   check the land against a real part, before the first order.
